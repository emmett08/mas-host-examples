# Recovery checkpoints

The trusted integration sidecar takes an immutable local cut every 30 seconds, at most 20 cuts per incident. It snapshots the controller and host SQLite stores with `VACUUM INTO`, retains admitted files as deduplicated content-addressed objects, checks hashes and rejects credential-shaped content, symlinks and oversized captures. The version 2 manifest maps each original relative path to its SHA-256, byte length and ordinary permission mode. Each `objects/<sha256>` payload occurs once per checkpoint, even when many MAS phase directories retain the same native runtime. Checkpoint objects are immutable and nonexecutable. Each individual database cut is consistent. The collection is **not an atomic transaction across controller, host and external services**.

Inside Actions, the official `@actions/artifact` client uploads immutable checkpoint artifacts while the incident is running. Version 6.3.1 documents a ten-artifact limit per job. This workflow reserves capacity for other diagnostic artifacts: at most six checkpoint uploads, approximately 120 seconds apart, plus a final cut when capacity remains. Local cuts retain their 30-second cadence. These are bounded attempts, not a guarantee that the remote service or a changing source store will always provide a usable cut. `checkpoint-summary.json` reports attempts, local cuts, acknowledged uploads and uploads acknowledged before controller completion. Integration fails if Actions produced no acknowledged during-run checkpoint.

The small local Node action supplies the job-scoped artifact runtime credential to the trusted checkpoint process. It does not export it to later workflow steps. The integration wrapper strips runtime artifact credentials before starting the controller, and the checkpoint process receives no provider key, GitHub publication token or kubeconfig. Generated code runs in the separate credential-free sandbox. Checkpoint artifacts are trusted operator recovery evidence; they can contain protected test material and must never become a repair-agent source projection or unrestricted UI disclosure.

Each upload has a durable intent and a distinct artifact name. Acknowledged receipts retain the artifact ID, service digest and manifest digest. A lost response remains `unknown` and is not automatically uploaded again under the same identity. Later periodic cuts are separate snapshots, not retries of the uncertain write. If a response is lost, retrieve that exact artifact name and verify its manifest before recording reconciliation. Do not infer upload success from an attempted request or local ZIP.

## Download, verify and restore

Use the exact run, repository and artifact name from the upload receipt or workflow log:

```sh
gh run download RUN_ID --repo OWNER/REPOSITORY \
  --name self-remediation-checkpoint-RUN_ID-ATTEMPT-MODE-SEQUENCE-MANIFEST_PREFIX \
  --dir /tmp/downloaded-checkpoint
node --import tsx scripts/checkpoint.ts --verify /tmp/downloaded-checkpoint
node --import tsx scripts/checkpoint.ts --restore /tmp/downloaded-checkpoint \
  --output /path/to/restored-run
```

Run these commands from `examples/self-remediation` in the exact trusted source revision identified by `checkpoint-manifest.json`. Compare its SHA-256 with the retained acknowledgement; a valid file hash alone does not establish who produced it. Restore verifies each distinct object once, then reconstructs only manifest-listed paths into an empty destination. It restores their recorded ordinary permission modes, including executable host runtimes, while SQLite stores are writable only by their owner. Setuid, setgid and other special mode bits are rejected; artifact-download permission normalization cannot grant or remove execution authority from the hash-checked manifest. It preserves recorded deadlines, consumed budgets, cancellation, pending phases and unresolved effects. It adds `RUNNER_LOSS_REQUIRES_RECONCILIATION.json`; `run.ts` rejects this marker before dispatch.

This restore command intentionally does **not** resume an incident on a replacement runner. Host project and invocation receipts contain the original absolute working/state paths. Container image state and kubeconfig are not checkpoints, and a new cluster has different object identities. The retained marker names the original paths, unresolved operations and any external image dependency. A retained `candidate-image.json` is metadata only: its checkpoint-hashed manifest describes the exact archive stream and each chunk, but `candidate-image.json.parts/` is deliberately absent from the checkpoint. Retrieve those separately retained chunks from the matching final workflow diagnostic artifact, verify the manifest SHA against `externalDependencies`, and use the image adapter to verify every chunk and the complete stream before loading. If that artifact was not acknowledged before runner loss, the image dependency is unavailable; preserve the recovery block and rebuild/reverify under fresh identities instead of claiming an exact-image restore. The operator must reconcile surviving GitHub branches/PRs/merges and Kubernetes effects, validate target identities, and rebuild/reverify any unavailable images or changed environment under fresh identities. Removing the marker without that evidence does not constitute recovery. Automatic cross-runner continuation is not implemented.

For an ordinary controller-process restart with the original runner, paths, host stores and external environment intact, reuse the same incident/output/configuration with `scripts/run.ts`. It reconciles retained invocation receipts before admitting new work. Cancellation prevents new admissions; an effect admitted before cancellation may still complete and must be reconciled.

## Bounds and exclusions

Each checkpoint admits at most 20,000 original file paths and 128 MiB of **distinct object bytes**. Logical copies of the same content consume one object allocation; they retain independent path and permission entries. Verification checks the manifest's `objectBytes` against the unique hashed payloads. The upload list contains exactly those unique objects plus the manifest and its digest, not one copy for every phase path. It includes the outer journal, tool-effect journal, host stores, source projections, CAS stores, immutable contexts and prior upload receipts. It excludes mutable log streams, Git databases, previous snapshot trees, kubeconfig, credentials, container runtime state and candidate image payload chunks. The small `candidate-image.json` manifest is included with a 64 KiB metadata bound and an explicit `externalDependencies` entry; no image payload bytes count toward the checkpoint's 128 MiB object cap. The final workflow diagnostic artifact separately retains the complete available replay, checkpoint index and upload acknowledgements, and, when produced, immutable image export. It excludes `durable-checkpoints/**`: acknowledged checkpoint cuts already have separate immutable remote artifacts, and reuploading all 20 local cuts would repeat large runtime objects across captures. An unacknowledged local cut is not claimed as remotely recoverable. A runner lost after the most recent acknowledged checkpoint can lose later observations; uncertainty remains blocking.

Local tests exercise live WAL snapshots, three identical phase runtimes stored and uploaded once, a 144 MiB logical capture admitted as approximately 48 MiB of unique bytes, rejection above 128 MiB of distinct bytes, restored executable modes, exact hash verification, pending phase/budget preservation, interrupted-restoration guards, credential/path rejection, explicit image-manifest dependency with excluded payload chunks, and lost-upload non-repetition. Actual Actions artifact acknowledgements and a runner-loss restore remain separate integration observations.
