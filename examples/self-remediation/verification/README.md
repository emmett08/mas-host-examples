# Finite controller verification

Run `python3 verification/verify.py` from the example with SPIN and a C compiler available. The report retains the model and implementation hashes, compiler invocations, exhaustive safety-search output and each required counterexample. CI retains this report even when later integration fails.

The three original models must pass with and without partial-order reduction. Twenty guard-removal controls must reach the intended assertion. Four deliberate failing assertions establish reachability of eligible recovery, a completed failed check followed by a new phase, and retained unknown or reserved effects across restart. A control is successful only when SPIN reports its expected assertion, rather than any unrelated error.

| Model property | Implementation correspondence | Important boundary |
|---|---|---|
| Candidate, requirement, test, environment and image equality | `controller/policy.ts` checks a verification receipt against the exact current identities before eligibility | Equality abstracts exact hashes. It does not prove the source implements the requirement. |
| Protected verifier and conjunctive mandatory gates | `controller/policy.ts` independently admits verifier authority and every mandatory result | A model opinion or candidate-authored test cannot replace a mandatory measurement. |
| Unknown effect blocks a new phase and another dispatch | `controller/journal.ts` `admitPhase`, `assertActive` and `intend` inspect durable intended/unknown effects | Reconciliation must establish completion or non-occurrence using external evidence. |
| Persistent budget and cancellation | `controller/journal.ts` `reserveBudget` and `cancel` survive process reconstruction | Restored runner snapshots preserve these rows but remain blocked pending cross-store/external reconciliation; see [RECOVERY.md](RECOVERY.md). Storage destruction is not an ordinary process restart. |
| One promotion owner | `controller/deployment.ts` `Deployment.baseline` calls `controller/journal.ts` `acquireTarget` before establishing the owned target; `trial` reserves the same target when the faulty baseline could not build | The model assumes SQLite transaction durability and a common target key. |
| Current target at effect boundary | `deploy/trial.ts` `KubernetesTrial.replace` sends atomic UID/resourceVersion/owner/image JSON Patch tests. `deploy/github.ts` checks base refs and supplies the expected PR head to merge. | GitHub provides no atomic base-SHA merge precondition. A changed merged tree requires fresh build/verification before deployment. |
| Current receipt identity at promotion | `Controller.run` retains `verified:<candidate tree>`, rechecks source/target freshness, then calls `Deployment.trial`. That adapter checks report-to-build tree/image equality; replaying a passed trial also requires fresh protected observations. `validateCandidate` in the publisher rehashes candidate bytes and checks its verification tree. | `promotion.pml` requires the whole tuple to remain current at dispatch. Requirements/test/environment identities remain frozen in the incident and retained receipt. Kubernetes replacements bind the image and candidate annotations. |
| Acknowledged claim required | Durable effect dispatch reserves before transport and does not infer permission from a lost acknowledgement | Unknown transport is distinct from a completed failing measurement. |

This is a correspondence argument, supported by implementation tests and hash binding in the report. It is not a machine-checked refinement proof. The models intentionally preserve separate dispatch, response loss, restart and reconciliation transitions. Two contending controllers, two process incarnations, two identity values and at most two budget units bound the state space. No general progress or wall-clock guarantee is claimed. Unbounded effects, storage loss, malicious infrastructure, cryptographic attacks and arbitrary generated-program semantics require other evidence.

Cancellation blocks new work admission. The promotion model separates admission from application of its external request, so an already admitted operation may complete after cancellation. The controller must retain and reconcile that result. Cancellation does not promise to retract an in-flight Kubernetes or GitHub request.
