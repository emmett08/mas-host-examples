# External effects and source publication

The trusted controller invokes `scripts/trial.ts`, `scripts/github-read.ts` and `scripts/publish.ts` through the pinned host's ordinary command adapter. Each adapter receives `--invocation` from the host's `{ invocation_id = true }` binding. The controller's operation ID, host invocation ID and controller-process attempt ID remain distinct in SQLite receipts. Source blobs, logs and image archives are retained outside the wire frame and referenced by content hash. The separate `externalCapabilities` registry declares input/output schemas, implementation, allowed resources, credential owner, effect class, bounds and reconciliation.

Every mutation records its intention before dispatch. A lost acknowledgement leaves an unknown effect. The existing operation can reconcile its exact branch, PR, merged commit or Kubernetes annotations. A new operation or phase cannot bypass the unresolved record. An absent resource alone does not prove that an outstanding remote request will never create it. Git blob/tree/commit creation is content-addressed, but a lost ordinary candidate-tree or commit response without a known expected SHA still blocks publication until an operator supplies authoritative object evidence. The adapters do not repeat these requests automatically.

`freezeIncidentSource` creates a genuine faulty commit in a separate bare object database before baseline evidence is frozen. It preserves all repository content outside the admitted application subtree. The snapshot presented to repair agents contains ordinary application files and has no Git object database. The retained object manifest lets the publisher import exactly the same faulty commit later. The publisher creates `demo/incidents/<run-id>` at that commit and targets the repair PR at that branch. The branch and every imported object are immutable at this interface. No branch update or force push is implemented. A repair that produces no changed Git tree is rejected.

Operational publication uses the actual deployed faulty commit and configured base branch. `pull-request` is the default policy used by the workflow wrapper. `archive` executes no GitHub writes. `automatic` is confined to the exact disposable incident branch, requires explicitly named checks and their owning GitHub App IDs, and requires an App credential. A check from another app or an earlier successful check superseded by a failure cannot admit a merge.

For an operational incident, `OperationalTargetGrant` admits one namespace, Deployment UID, Pod UID, container, immutable image and source revision. The read-only collector verifies the Pod's ReplicaSet and Deployment ownership chain, checks an optional exact triggering Event and compares the deployed and running image digests. The configured source annotation must occur on both the Deployment template and the Pod. That annotation is an assertion of the build/deploy interface and requires supporting build provenance. Hashes bind the complete declared workload configuration and actual Pod specification without publishing environment values or secret contents. Operational publication repeats this read before repository writes and rejects changed source, image, configuration, generation or Pod identity. Status-only resourceVersion changes are recorded without being confused with a release change.

`SELF_REMEDIATION_SOURCE_KUBECONFIG` selects the source cluster and falls back to `KUBECONFIG`. The isolated trial continues to use `KUBECONFIG`. Both are available only to their declared trusted native adapters. The initial operational adapter rejects mounted-data dependencies, secret-derived environments and process overrides that the isolated baseline cannot reproduce. An explicit matched sandbox adapter is required before extending that domain.

GitHub's merge endpoint accepts an expected head SHA but has no atomic expected-base-SHA parameter. The adapter checks the current base immediately before the merge and checks the resulting tree afterwards. A concurrent base change can therefore result in `merged-tree-changed`. That outcome blocks deployment and requires a new build and verification. This API boundary is narrower than Kubernetes' atomic UID/resourceVersion JSON Patch tests. The finite controller model's atomic target-precondition assumption does not prove atomic GitHub base comparison.

The GitHub workflow publishes in a separate process/job that never runs candidate code. An optional third promotion job has no provider or GitHub publication credentials. It accepts only an exact-tree merge receipt, verifies the retained image archive, imports it into a fresh disposable cluster and repeats protected HTTP observations. `merged`, `trial recovered` and `deployed recovery verified` remain separate outcomes.

Automatic mode polls required checks for at most three minutes and eighteen reads. Every fresh read has a distinct admitted host invocation and retained receipt. Once checks pass, a separate merge invocation acts on the frozen PR head, base, tree and check policy. The original completed `awaiting-checks` invocation is never reused to admit a new mutation. The check deadline persists across process restart. Exhaustion retains `awaiting-checks`, keeps promotion blocked and preserves the request and PR identity. An explicitly resumed controller can start a fresh bounded `checks` phase and then a `merge` phase using those retained identities. An unresolved effect must be reconciled before either admission.

## Runtime GitHub access

The ChatGPT GitHub plugin used during implementation is separate from runtime access. `OfficialGitHubMcp` connects to GitHub's official `https://api.githubcopilot.com/mcp/` endpoint using `SELF_REMEDIATION_GITHUB_READ_TOKEN`. The single exposed operation is `actions_get` with `method=get_workflow_run`, one fixed repository, one run ID and one workflow-source SHA. The returned projection contains only run identity and status. It exposes no source, history, search, logs, downloadable artefacts or resource links. This metadata scope is valid during blind injected evaluation even when the workflow itself originates from healthy main. A source read from healthy main is never granted.

Trusted setup must freeze the SHA256 of `{name:"actions_get",inputSchema:<discovered schema>}` in `GitHubReadGrant.toolSchemaSha256` before starting a phase. Discovery cannot add a capability or replace that value. A changed schema stops the adapter and reports the observed digest for a separate reviewed configuration update. Lack of a credential, service availability or the admitted schema is an unavailable external integration, not a fabricated successful MCP demonstration.

The trusted REST publisher uses only `SELF_REMEDIATION_PUBLISH_TOKEN`. Candidate execution receives neither token. Configure a repository-scoped GitHub App installation with contents write, pull requests write and checks read permissions. Set `SELF_REMEDIATION_APP_CLIENT_ID`, `SELF_REMEDIATION_APP_PRIVATE_KEY` and the required-check specification in the protected publication environment. For example, `SELF_REMEDIATION_REQUIRED_CHECKS` is JSON of the form `[{"name":"protected-contract","appId":12345}]`, with the actual check name and actual trusted app ID.

GitHub's token-trigger rules were checked against its official documentation on 18 October 2026. `GITHUB_TOKEN`-originated pushes do not start ordinary push workflows. PR `opened`, `synchronize` and `reopened` events create approval-required workflow runs. A separate GitHub App token permits downstream PR workflows to run unattended. The dedicated self-healing workflow excludes repair-branch pushes and never enables live credentials for a pull request. These rules are not a substitute for repository permissions or required checks.

## Disposable image trials

The trusted image adapter transfers an already built Docker config digest to the one-server k3d cluster. It reads the imported containerd manifest, checks `manifest.config.digest` against the build result, creates an immutable `repository@sha256:manifest` alias and uses that alias in the Pod. The observation also checks the actual container `imageID`. Exported Docker archives retain their raw SHA256 and config digest. Restoring an archive verifies those identities before loading it.

Trial resources are confined to `mas-repair-*` namespaces. Pods have no service-account token or credential environment, run as UID/GID 10001, use a read-only root filesystem, drop all capabilities, forbid privilege escalation, use the runtime seccomp profile and have CPU/memory limits. A namespace policy denies ingress and egress. The verifier reaches the Pod through a trusted loopback `kubectl port-forward`. Candidate programs have no host mounts or Docker socket. The cluster's network-policy implementation is an environmental assumption which the integration environment must enforce.

The application is stateless and all trial data are disposable. There are no shared persistent volumes or schema migrations. Replacing an image does not reverse arbitrary data changes. Existing-target replacement uses atomic JSON Patch tests for UID, resourceVersion, promotion owner and previous image. Lost patch replies reconcile only against the exact operation, host invocation and candidate/image identity. A fresh observation is always required after deployment.

HTTP criteria are supplied by the independent verifier. Each expected JSON object describes required properties, and an expected array specifies its exact length and element values. Additional object properties are allowed consistently with the protected baseline verifier. Transport loss produces an inconclusive observation. An observed failing response is a completed failed criterion. Diagnostics remain content-addressed artefacts rather than oversized host messages.

## Validation scope

`tests/publication.test.ts` exercises successful nonempty publication, create-only refs, lost branch/PR/merge replies, candidate and base staleness, inconclusive gates, automatic-mode restrictions, unresolved-effect admission, Kubernetes resourceVersion and effect-identity reconciliation, frozen MCP discovery and metadata redaction. The fake transports test control behaviour, not GitHub or cluster availability. The workflow's real host/k3s integration and manually authorised provider/publication modes are separate acceptance gates. A few fixture cases do not establish general LLM repair competence.
